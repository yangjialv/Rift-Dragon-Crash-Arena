# Rift Dragon Crash Arena

## 敌人 AI 系统详解

版本：重构前技术说明 v1.0 ｜ 日期：2026-10-16 ｜ 引擎：Unreal Engine 5.3

本文在标准行为树重构开始前生成。它同时介绍当前代码与已经确认的目标设计，所有“目标方案”均不代表代码已经完成。
工作分支为 refactor/gas-3c；当前已有 38 组自动测试通过，但原关卡启用新 AI 后的完整实机验收仍需确认。

## 1. 项目与敌人 AI 的目标

这是一个单人、圆形竞技场 Boss 战 Demo。玩家控制可以跳跃、冲刺、吸附表面的液态史莱姆，借助随机生成的空间锚点调整位置，再在龙的弱点开放时发起重撞。

目前敌人 AI 的主角是一只位于竞技场中心的龙，不是巡逻、寻路和搜索敌人的普通 NPC。AI 的任务是组织攻击节奏，让玩家阅读预警、躲避攻击、利用锚点接近弱点，并在两个阶段中应对逐渐增加的压力。

一个完整循环可以用人话描述为：龙出几招，玩家躲避；龙露出破绽，玩家反击；反击成功后更新血量和阶段，继续下一轮。

系统是规则驱动的游戏 AI，不是机器学习模型，也不是让大语言模型在游戏运行时决定每一招。随机选招也只在预先约束的范围内发生。

## 2. 先解释几个名称

| 名称 | 人话解释 | 在本项目中的作用 |
|---|---|---|
| Actor | 场景中的一个对象 | 地板、锚点、弹丸和龙都属于这个基础体系 |
| Pawn | 可以被控制的 Actor | 让龙具备被 AIController 控制的资格 |
| AIController | 电脑控制角色的对象 | 管目标、运行行为树和清理控制过程 |
| Behavior Tree | 按条件选择行为的决策图 | 决定等待、按阶段选招和执行攻击 |
| Blackboard | 行为树共享的便签 | 记录目标、阶段、眩晕等决策信息 |
| Decorator | 分支入口上的条件 | 比如“正在二阶段”“玩家目标是否存在” |
| Service | 分支运行期间的低频维护 | 比如检查目标是否已经失效 |
| Task | 树上真正执行一步动作的节点 | 比如选下一招、发起技能并等待完成 |
| GAS | UE 的技能与效果管理系统 | 管技能开始、结束、取消、生命和伤害 |
| ASC | 角色的 GAS 管理组件 | 保存技能、属性和状态效果 |
| Gameplay Cue | GAS 的表现通知 | 播放声音、火焰、受击闪光等 |
| Montage | 可调度的动画片段 | 龙的待机、攻击、眩晕、死亡动画 |

行为树不属于 GAS；两者协作。行为树决定“现在做什么”，GAS 负责“这个技能怎样合法地开始、执行和结束”。黑板也不是第二份血量系统。

## 3. 当前已经实现的分工

| 当前文件或组件 | 现有职责 |
|---|---|
| RDCABossPawn | 原 Boss 蓝图的 Pawn 父类，查询已有 ASC，不新增第二套身体和碰撞 |
| RDCABossAIController | 创建/运行原生树，找玩家，同步黑板，管理决策控制权 |
| RDCABossBTNodes | 原生等待、分阶段选招、GAS 执行任务，以及混合查询条件 |
| BossEncounterComponent | 攻击选择规则、轮次、状态时间、原参数和底层攻击执行兼容代码 |
| RDCABossAttackAbility | 三类 Boss 技能的共同生命周期 |
| BossWeakPointComponent | 弱点碰撞、开放条件和有效重撞伤害，生命来自 GAS |
| BossAnimationComponent | 监听战斗状态，调度原有蒙太奇 |
| BossFanProjectile | 弹丸的直线、曲线、追踪和贴地飞行 |
| BossSweepLaser | 激光预警、伤害范围、火焰表现与扫射 |

当前树是真正使用 UE 行为树组件运行的树，但由 C++ 在运行时创建，没有内容浏览器中可打开的树图资产。

它的逻辑是：先处理禁止出招、弱点开放和已有技能；正常情况下等待恢复，选择阶段策略，调用选招，再执行 GAS 技能。释放任务目前逐帧查询本次执行编号是否结束。

现有 AI 接管后，Encounter 的旧 Tick 不再自己选下一招。技能与碰撞的持续更新仍由原执行路径推进。这样避免两个“大脑”同时发起攻击。

用户已确认 Boss 从 Actor 换为 Pawn 后正常。可视化 BT/BB、完全按黑板判断、目标传给技能和事件式任务结束，属于下一轮重构目标。

## 4. 开场、阶段和状态

### 4.1 开场

开场先禁止玩家移动和 Boss 出招，龙在地面待机，再起飞，脚下中心盘碎裂。开场导演负责协调动画和场景，AI 只遵守 Hold，也就是“暂时不允许出招”。

Hold 不是 P 键的全局暂停。Hold 时场景和动画可以继续更新；全局暂停则停止游戏时间。两种机制不能混为一谈。

### 4.2 两阶段

默认设计里，玩家和 Boss 的初始生命都是 5；Boss 的二阶段阈值默认是 3。实际关卡以蓝图保存的配置为准，不保证始终等于代码默认值。

一阶段位于赛博世界，强调教学；二阶段切换到源码世界，使用更复杂的弹幕和二重冲击波。场景扩散、天空和材质由场景系统负责，AI 在转阶段 Hold 期间不能出招。

### 4.3 当前战斗状态

| 状态 | 含义 |
|---|---|
| Idle | 初始空闲或弱点命中后的重新组织 |
| SelectingAttack | 已允许选择下一招 |
| Preparing | 攻击预警和前摇；激光还包含停顿 |
| Attacking | 正式执行攻击 |
| Recovery | 招间恢复 |
| WeakPointExposed | 眩晕、弱点开放，玩家可以反击 |
| Dead | Boss 死亡，不再攻击 |

这些状态继续为动画、HUD 和场景提供兼容通知。引入行为树不意味着要删除所有状态；行为树负责决策结构，技能和战斗过程仍有真实状态。

## 5. 当前攻击选择规则

### 5.1 一阶段：主要是编排，不是全随机

Boss 尚未受到有效弱点伤害时：旧版瞄准连射，恢复，单次冲击波，然后眩晕。

Boss 已受到伤害但还没进入二阶段时：预判弹幕或缺口弹幕，恢复，激光，然后眩晕。重复这一轮时优先换另一个基础弹幕，避免原样重复。

一阶段的玩家地面/空中/附着权重配置目前主要用于异常回退，不是正常教学流程的主要决策来源。

### 5.2 二阶段：先抽大类，再抽子类型

默认大类权重为：弹幕整体 0.5，冲击波 0.3，激光 0.2。抽中弹幕后，再从本轮尚未使用的五种高级弹幕中等概率选择一种。

一轮默认完成三次攻击后进入眩晕。同一种弹幕不能在该轮重复，冲击波和激光各最多一次，但不同弹幕可以在同一轮出现。

“五种弹幕”不等于给弹幕五份大类权重。先抽类别正是为了避免弹幕数量越多，冲击波和激光就越难出现。

### 5.3 权重不是每次都固定的百分比

若本轮已经放过波，波被排除，剩余弹幕 0.5、激光 0.2，实际概率约为 71.4% 和 28.6%。用过某一种弹幕，只排除该子类型，不自动降低弹幕大类的 0.5。

缺少弹丸类或激光类会限制可选攻击。调试开关可以直接强制某种弹幕或激光。随机种子用于复现选择序列，不是增加某一招的权重。

当前不会按玩家距离、移动方向、速度、生命或锚点数量动态增加某招权重。某些因素参与瞄准，但不参与攻击类别选择。以后若加入战术权重，需要单独设计，不能将计划功能说成现有功能。

## 6. 攻击池与技能执行

### 6.1 八种弹幕

| 弹幕 | 轨迹特点 | 主要阶段 |
|---|---|---|
| Legacy Aimed Volley | 朝锁定目标方向连射 | 一阶段 |
| Predictive Volley | 根据目标运动进行预判 | 一阶段 |
| Gap Wall | 用弹墙保留可读的安全缺口 | 一阶段 |
| Curved Volley | 发射后在限定角度内弯曲 | 二阶段 |
| Homing Volley | 先散开，再进行有时间和角度限制的追踪 | 二阶段 |
| Rotating Gap Wall | 不同波次让缺口旋转移动 | 二阶段 |
| Double Spiral | 两组旋臂形成连续空间压力 | 二阶段 |
| Legacy Dense Fan | 密集扇形封锁正面区域 | 二阶段 |

这些模式共用已有弹丸蓝图体系，不要求八套完全不同的模型。

### 6.2 冲击波

冲击波从固定的地面参考位置扩散，使用参数化环形视觉和实际伤害判定。二阶段强化为同一次技能中的两个连续波：共用一次预警，两个波可以同时存在，最后一个波结束才算整招完成。

如果把两个波拆成两个完整攻击，就会重复前摇、延长间隔并错误增加轮次计数，这不是当前设计。

### 6.3 激光/龙焰

预警阶段允许龙跟随玩家转向；预警结束后锁住方向，进入停顿；停顿结束时再判断玩家是否仍处于预警区域，决定直射或有限角度的横扫。

目标是为玩家提供可阅读的走位机会，而不是无限追踪。龙嘴 Socket、激光体积、地面预警、下降和回升均有不同职责，不能用一个随头部摆动的投影替代所有判断。

## 7. 弱点、伤害与反击循环

只有符合条件的锚点重撞，并且命中开放弱点，才会造成有效弱点伤害。碰到身体则按身体响应反弹，不能把任何与 Boss 的接触都算成伤害。

GAS 保存唯一实时生命；弱点组件保留碰撞与资格判断。这样表现层显示“开放”并不等于绕过伤害校验。

攻击正常完成才增加轮次计数。达到本轮招数时，在技能完成处理流程里立即开放弱点，不能等一段恢复时间，也不能等低频 AI 服务发现。

有效弱点命中后立即结束眩晕，重置轮次和去重记录；没有命中则在窗口超时后重置。血量达阈值时场景进入转阶段，AI 通过 Hold 遵守切换过程。

取消技能不计为完成，不凭空开放弱点。每次释放都有独立身份，旧任务只能取消自己拥有的那次技能。

## 8. 当前黑板实际用在哪里

当前 Controller 写入七个字段：TargetActor、CombatPhase、EncounterState、IsHeld、IsStopped、IsExecutingAttack、IsWeakPointExposed。

现有条件节点真正读取的是 CombatPhase、IsExecutingAttack、IsWeakPointExposed。禁止出招、等待时间等仍会直接查询 Encounter；目标虽然写入黑板，攻击代码仍有全局玩家查询。

因此当前属于混合过渡实现，而不是已经完成的统一黑板决策方案。这个区别是本轮标准重构的直接原因。

## 9. 下一轮标准方案：可视化树与完整决策接口

目标是提供可以在编辑器中打开的 BT_RiftDragonCombat、BB_RiftDragonCombat 和控制器配置蓝图。代码负责稳定的节点和接口，资产负责分支与条件配置。

### 9.1 树的组织

```text
Root / 优先级选择
  1. 战斗结束 -> 禁止新动作并等待关停
  2. Hold -> 等待开场或转阶段结束
  3. 没有目标 -> 等待有效目标
  4. 正在眩晕 -> 等待反击窗口关闭
  5. 正常战斗，依次执行：
       等待出招时机
       按一阶段/二阶段策略选择攻击
       按选定类别激活 GAS 并等待完成
```

技能执行任务本身会保持“正在执行”，不再通过一个抢占分支检查“忙碌”而把自己的攻击取消。

### 9.2 目标黑板字段

| 字段 | 用途 |
|---|---|
| TargetActor | 选招和技能使用的真实目标 |
| IsBattleOver | 最高优先级禁止出招 |
| IsEncounterHeld | 开场/转阶段门禁 |
| IsStunned | 进入或离开反击窗口分支 |
| CombatPhase | 选择阶段策略 |
| NextActionTime | 下一次允许出招的游戏时间 |
| SelectedAttack | 弹幕/波/激光执行分支 |
| SelectedBarragePattern | 本次弹幕的具体轨迹模式 |
| HasAttackPlan | 防止同一轮决策被重复随机或消费 |

所有字段独立于其他 Boss 实例。生命、轮次计数和去重集合不复制进黑板作为第二份权威数据。

### 9.3 事件驱动是什么意思

事件驱动就是“事情发生了再通知”，例如 Hold 改变、目标死亡、技能完成时，相关系统直接通知 AI。不是让每个条件每帧问一遍同样的问题。

Controller 订阅战斗事件来更新黑板；UE 自带的黑板条件观察键值变化；任务订阅带身份的技能完成/取消事件。低频服务只校验目标等兜底事项。

技能内部追踪弹、扫射、波扩散仍需持续更新，事件驱动不会删除这些必要的 Tick。

### 9.4 中断规则

死亡、Hold 和目标丢失必须能够中断出招。阶段选择和已选攻击不应在执行中随意重抽。正常每轮结束的眩晕是最后一招成功后的结果，不能反过来把这招记为取消。

Observer Aborts 是 UE 条件节点的中断配置：Self 中断当前分支，Lower Priority 抢占低优先级分支，Both 两者兼有，None 则不主动抢占。每个条件按游戏语义设置，不是全部设成 Both。

## 10. 安全性、生命周期与常见问题

### 10.1 同一角色只能有一个决策来源

树接管后旧 Tick 不再自主选招。正式资产模式若配置错误，应明确报错并停止，不能偷偷用旧大脑继续攻击，导致测试者误以为接入成功。旧模式仅通过明确的迁移开关使用。

### 10.2 完成通知必须绑定具体攻击

不能听到“任意技能结束”就结束当前任务。要同时验证本次计划、技能或执行编号；先登记监听再激活，以处理激活过程中同步结束的技能。

### 10.3 退出路径同样重要

成功、失败、中断、死亡、失去控制、关卡结束、Restart 都要清理监听和未消费计划。任务中保存的可变状态必须按 AI 实例隔离，不能放到多个 Boss 共用的模板里。

### 10.4 时间只有一份

技能时间由 GAS 执行路径管理；恢复/窗口只有一个真实时间来源。等待任务只等待该来源，不另算一份同名冷却。游戏暂停时这些等待也应暂停。

### 10.5 AI 不替代碰撞和动作系统

行为树不会自动修复弱点碰撞、龙嘴方向、地面高度和镜头取景。它决定何时发起行为，运动、碰撞、技能和表现仍各有自己的职责。

## 11. 怎样调试与验收

当前版本可查日志 Boss AI behavior tree started，或查询 Encounter 的 Is Behavior Tree Driven。仅看到 Boss 会攻击不足以证明行为树接管，因为旧流程也能攻击。

标准资产版本应能在 Play 时打开树，选择运行实例，看到当前执行节点以及黑板变化。应重点观察目标、阶段、Hold、眩晕和攻击计划是否与场景一致。

已有测试报告位于 rdca/Saved/Automation/GASBossAI/index.json，已有 38 组通过；这是无渲染自动测试，不能证明真实画面、声音和所有手感已经验收。

新增标准重构验收：黑板变化触发中断；任务目标真实传给技能；同步完成不会卡树；双波计数一次；最后一招立即眩晕；旧任务不取消新招；共享树的两个 Boss 不互相干扰；退出后无残留监听。

实机必须打完两阶段，并覆盖玩家死亡、Boss 死亡、P 暂停、胜利落地和 Restart。Shipping 编译通过不等于 Cook、资源引用和独立打包已经通过。

## 12. 技术表达与实施顺序

可以这样介绍当前项目：它基于 UE Gameplay 的 Pawn/Controller/Component 分工，使用 GAS 管理生命和技能，使用原生行为树组织固定竞技场 Boss 的两阶段决策，并通过 Gameplay Cue 统一关键音效和特效通知。

不能在标准重构完成前宣称“已提供完整可视化树”“所有条件都通过黑板”“攻击已统一使用黑板目标”。这些是本轮待实现目标。

实现顺序：目标与完成事件接口，事件式任务和目标服务，可视化资产，正式切换，自动与实机验收。保存原参数与用户资产，不把 AI 重构扩大成重新制作模型和动画。

继承体现在 Boss Pawn 基于 Pawn、Controller 基于 AIController、三类技能基于共同技能基类；组合体现在龙由弱点、动画、战斗、ASC 等组件协作；多态体现在不同技能实现同一开始/更新/结束契约。

本项目当前是单机 Demo，不宣称已完成联机 AI、多人 GAS 复制、移动预测或自动学习型敌人。
